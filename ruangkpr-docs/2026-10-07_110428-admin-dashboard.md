# ruangKPR Admin Dashboard Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

> **Revisi 2026-10-07:** dokumen ini sudah diselaraskan dengan kode (`src/data/*`, `src/app/App.jsx`, `src/domains/mortgages/derive.js`). Enum, field, dan file mengikuti kode serta doc 04, bukan sebaliknya. Fakta yang mengikat ada di §0.

**Goal:** Membangun dashboard `super_admin` dalam frontend ruangKPR yang sama pada route `/admin`, dengan layout terpisah untuk operasional pengajuan, pengguna, master bank/produk, artikel edukasi, laporan, dan konfigurasi versioned.

**Architecture:** Pertahankan boundary tunggal `src/data/api.js`; UI admin tidak boleh mengakses `mockDb`, `localStorage`, atau kalkulasi langsung. Tambahkan domain admin terpisah tetapi reuse komponen visual dan token yang sudah ada. Mock admin API menjadi kontrak sementara; backend tetap menegakkan RBAC, ownership, state transition, audit, dan kalkulasi authoritative.

**Tech Stack:** Vite 8, React 19, React Router 7, JavaScript, Tailwind CSS 4, shadcn/Radix yang sudah terpasang, Vitest, Playwright.

## 0. Baseline kode yang mengikat plan ini

Dicek terhadap kode pada 2026-10-07. Bila bagian lain dokumen ini bertentangan dengan poin di bawah, kode dan doc 04 yang dipakai.

Dokumen hanya disimpan sebagai metadata, tanpa file bytes. → Sudah diubah di Phase 0 menjadi banyak akun di satu browser (§7 *Mock data model*); preview/download file asli tetap tidak bisa di-mock (§4.3).
- **Status aplikasi sudah ada.** `PRIMARY_FLOW`/`TAKEOVER_FLOW` di `mockApi.js`, `IN_PROCESS` di `selectHomeState.js`, doc 04 §9.1. Cancel = hard delete pre-akad. → Admin memakai enum yang sama (§1, §4.3). Tidak ada status `verification` maupun `cancelled`.
- **Transisi sudah ada sebagai dev control.** `mockControls.advanceApplication / rejectApplication / requestDocument` sudah push activity ke user, mengatur `pendingActions`, dan memanggil `completeApplication()` saat `disbursed`. → Logika ini diangkat jadi helper bersama admin + DevPanel, bukan ditulis ulang.
- **Konvensi kontrak vs mock berbeda.** Doc 04: `snake_case` + Money `{amount, currency, scale}` + envelope. Mock: camelCase + integer Rupiah, data dikembalikan langsung, error lewat `ApiError`. → Kontrak REST §5 tetap snake_case; operasi mock admin mengikuti `mockApi.js`. Konversi jadi tugas `httpApi` nanti.
- **Session tanpa role.** `auth.getSession` → `{status, user, verification}`. Login hanya OTP `/register` → `/verify`; tidak ada password atau Google. → `role` sudah ditambahkan di Phase 0; tidak ada `/admin/login` (§3).
- **Katalog statis.** `BANK_PRODUCTS` di `catalog.js`, dibaca runtime lewat `productsOf(db)`. Bank tertanam di produk (`product.bank = {id, name, mark}`), status produk `active: boolean`, `version` dicek saat submit. → Produk pindah ke `db.products` (§4.4).

- **KPR Health dihitung di frontend.** `healthScore()` di `derive.js` memakai band hardcode, dipanggil lewat `deriveMortgage()` dan langsung dari `optimize/insights.js`. Snapshot dashboard tidak membawa versi kalkulasi. → Config jadi parameter `healthScore()` (§4.7).
- **Konstanta yang akan jadi config.** `DEFAULT_REMINDERS` (`seed.js`), `MAX_FILE_BYTES`/`ACCEPTED_TYPES`/`ACCEPTED_EXTENSIONS` (`documentRules.js`), `CAPACITY_RATIO_BPS`/`STALE_AFTER_DAYS`/`OLD_BANK_POLICY` (`catalog.js`). Set milestone `FIXED_MILESTONES` (`derive.js`, `widgetData.js`) tetap konstanta. → Isi Configuration (§4.7).

## 1. Keputusan produk yang sudah dikunci

- Role: `user`, `super_admin`, dan `content_writer` (ditambahkan 2026-10-07: hanya modul Articles). Peta akses ada di `src/data/roles.js`.
- Admin berada di repo/frontend yang sama, route `/admin`, tetapi memakai layout/navigation terpisah dari B2C.
- Modul fase pertama: Overview, Users, Applications, Banks & Products, Educational Articles, Reports, Configuration, Audit Log.
- Super admin boleh melihat dan mengubah profil serta data finansial user.
- Admin login memakai alur OTP yang sama; role datang dari session. `super_admin` tidak memakai layar B2C.
- Workflow aplikasi mengikuti doc 04 §9.1 dan `mockApi.js`, tanpa enum baru:
  - Primary: `submitted → docs_verification ⇄ additional_docs_requested → bank_processing → appraisal → approved → akad → disbursed`.
  - Take Over/Top-up: `… → approved → old_mortgage_settlement → akad → disbursed`.
  - `rejected` hanya dari `bank_processing` atau `appraisal`.
  - Cancel tetap aksi user (hard delete pre-akad, keputusan produk saat ini); admin tidak membatalkan.
- Admin boleh review dokumen, meminta revisi (`additional_docs_requested`), memberi catatan internal yang tidak pernah terlihat user, dan mengubah status melalui transition yang valid (§4.3).
- Lifecycle bank product: `draft → published → archived`; published product tidak di-hard-delete. Bank sendiri hanya `active`/nonaktif.
- Reports: user, applications, conversion, dan produk bank.
- Konten MVP: artikel edukasi saja.
- Konfigurasi mencakup default reminder, aturan upload, parameter produk, serta bobot/threshold KPR Health (§4.7).
- Perubahan KPR Health wajib versioned: draft → preview fixture → publish → audit → rollback. Tidak ada perubahan langsung terhadap rumus produksi.

### Global guard

Ikuti pola `RequireAuth`/`GuestOnly` di `src/app/App.jsx`; tidak perlu file guard terpisah.

1. `SessionProvider` sudah menahan render sampai session tersedia, jadi guard tidak butuh state loading sendiri.
2. `RequireAuth admin` (guard yang sama dengan flag `admin`): guest → `/register` (alur OTP yang sama), `pending` → `/verify`, role non-staff → halaman 403 (bukan redirect diam-diam).
3. `RequireAuth` (B2C) mengarahkan staff ke home role-nya (`/admin` untuk `super_admin`, `/admin/articles` untuk `content_writer`). Ini sekaligus menangani redirect setelah OTP, karena `GuestOnly` mengirim user yang sudah login ke `/`. Di dalam layout, modul di luar akses role menampilkan "Halaman ini di luar akses kamu"; `/admin` (Overview) mengarahkan writer ke home-nya.
4. Setiap operasi admin tetap mengecek role di data layer (mock: `call(..., { admin: true })` khusus super admin, `{ admin: 'articles' }` juga untuk role yang memegang modul itu → selain itu 403 `FORBIDDEN`; backend: RBAC). Route guard frontend hanya UX.

### Responsif

- ≥1024px: sidebar admin tetap (pola `AppShell`).
- <1024px: navigasi menjadi baris horizontal yang bisa di-scroll (tanpa komponen baru); tabel berada di dalam card dengan scroll horizontal dan kolom sekunder disembunyikan.
- Touch target ≥44px. Tidak ada bottom nav B2C di dalam admin.

## 4. Screen specification

### 4.1 Overview

Kartu ringkas:
- total user terdaftar (tidak ada data "aktif"/last active);
- pengajuan perlu review;
- dokumen perlu tindakan;
- pengajuan per status;
- conversion submitted → approved → disbursed;
- produk published/draft/expired;
- perubahan konfigurasi terakhir.

Tabel kerja:
- Pengajuan terbaru yang perlu tindakan.
- Produk yang segera kedaluwarsa.
- Aktivitas admin terbaru.

Tidak ada chart dekoratif. Maksimal 1 funnel conversion dan 1 tren aplikasi bila datanya memang tersedia.

Status implementasi ada di Phase 2 (§8): aktivitas admin, perubahan konfigurasi, dan tren menyusul saat datanya ada.

### 4.2 Users

List:
- search nama, email, atau nomor HP (`user.contact` bisa telepon atau email);
- filter punya/tidak punya pengajuan aktif dan KPR aktif;
- kolom nama, kontak, pengajuan aktif (status), KPR aktif, dibuat;
- kontrak memakai pagination cursor; mock mengembalikan array penuh (`admin.users.list`, sudah ada sejak Phase 0).

Tidak ada filter "status akun" dan kolom "last active": datanya tidak ada dan MVP tidak punya aksi suspend.

Detail:
- account identity (`user.contact` + `contactType`, read-only);
- profile (NIK dimasking default);
- finance sesuai field yang ada di mock: `monthlyIncome`, `jointIncome` (boolean), `partnerIncome`, `vehicleDebt`, `cardDebt`, `otherDebt`, `routineExpenses`, `emergencyFund`. Di kontrak doc 04: `monthly_income`, `partner_monthly_income`, dst. sebagai Money object;
- aplikasi terkait;
- mortgage terkait;
- audit perubahan.

Edit:
- konfirmasi sebelum simpan (`ConfirmDialog`);
- `expectedVersion` untuk conflict; record user di mock perlu field `version` baru;
- alasan perubahan wajib;
- finance disimpan lewat logika `profile.update` yang sudah ada, yang ikut menyinkronkan `mortgage.finance` untuk mortgage draft/aktif. Ekstrak jadi helper, jangan diduplikasi; tanpa ini KPR Health user tidak berubah;
- response membawa recalculation marker bila field finance berubah;
- kontak login (`user.contact`) tidak bisa diedit dari layar ini karena itu identitas OTP.

### 4.3 Applications

Queue filters:
- status (enum §1);
- product type: `primary`, `takeover` (top-up = `optimizationMode: 'topup'`);
- bank/product;
- pending action (`pendingActions` tidak kosong);
- submitted date;
- search user/application ID.

Detail:
- user summary;
- data application snapshot (`app.snapshot`: data, selection, `productVersion`, `calculationVersion`);
- selected product (`app.selection`);
- documents checklist dari `requiredDocuments(app)` + status per dokumen (`uploaded | verified | needs_update`). Mock hanya punya metadata (nama file, ukuran, tipe); preview/download hanya untuk backend nyata;
- status timeline dari `statusHistory` (reuse `Timeline`/`StatusStepper` di `components/shared/progress.jsx`);
- admin notes (disimpan terpisah dari aplikasi, §6);
- transition actions dari `allowedTransitions`.

Transition matrix — satu map di data layer, dipakai admin dan `mockControls`. Semua transisi wajib `reason` untuk audit.

| Dari | Ke | Input tambahan | Efek samping (helper yang sudah ada) |
|---|---|---|---|
| `submitted` | `docs_verification` | — | activity dari `STATUS_COPY` |
| `docs_verification` | `additional_docs_requested` | `documentTypes[]`, pesan ke user | dokumen → `needs_update` + `invalidReason`; `pendingActions[{type: 'document_update'}]`; activity "Bank minta dokumen tambahan". Re-upload dari B2C otomatis kembali ke `docs_verification` (sudah ada di `applications.uploadDocument`) |
| `docs_verification` | `bank_processing` | — (ditolak bila `pendingActions` masih ada) | activity |
| `bank_processing` | `appraisal` | — | activity |
| `appraisal` | `approved` | — | activity |
| `approved` (takeover) | `old_mortgage_settlement` | — | activity |
| `approved` (primary) / `old_mortgage_settlement` | `akad` | angka final akad (§12 Q1) | activity; angka final disimpan di aplikasi |
| `akad` | `disbursed` | — | `completeApplication()` → mortgage aktif; takeover menandai KPR lama `replaced`; aturan satu KPR aktif per akun tetap berlaku |
| `bank_processing` / `appraisal` | `rejected` | `code`, `displayReason` | `rejection {code, displayReason, relevantStep, rejectedAt}` yang dibaca B2C (`ApplicationTracker`, `HomePage`, `meta.js`, `retrySameBank`); activity |

Catatan:
- `relevantStep` diturunkan dari `code` lewat map kode → step, bukan diisi admin. Kontrak doc 04 memakai `relevant_fields`.
- `mortgageFromApplication()` sekarang memakai `app.selection` (angka simulasi), padahal doc 04 §9.1 mewajibkan angka akad final. Setelah transisi `akad`, helper itu memakai angka final bila ada.
- `mockControls.rejectApplication/requestDocument` sekarang lebih longgar (semua status `IN_PROCESS`); setelah refactor keduanya mengikuti matrix ini.
- Internal note bukan transisi: operasi terpisah, tidak mengubah status.

Transition tidak valid harus 409/422; UI hanya menampilkan tombol dari `allowedTransitions` di response.

### 4.4 Banks & Products

Bank (tanpa lifecycle draft/published):
- `id`, `name`, `mark` (kode pendek yang dipakai `BankMark`), `active`;
- daftar bank awal diturunkan dari `product.bank` yang sudah ada; edit lewat `FormDialog` di `/admin/banks`;
- bank nonaktif = semua produknya tidak ikut matching.

Product fields mengikuti shape `catalog.js`:
- `bank`;
- `name`;
- `productTypes`: `primary` | `takeover`;
- `scheme`: `conventional` | `sharia`;
- `ratePeriods[]`: `{type: 'fixed' | 'floating', durationMonths, rateBps, estimated}`;
- `fees`: primary `provisionBps`, `admin`; takeover menambah `appraisal`, `notary`, `insurance`;
- `eligibility`: primary `minimumIncome`, `maximumDtiBps`, `maximumLtvBps`, `minimumAge`, `maximumAgeAtMaturity`, `maximumTenorMonths`, `occupations`, `propertyTypes`; takeover `maximumDtiBps`, `maximumLtvBps`, `maximumTenorMonths`, `purposes` (top-up);
- `effectiveFrom`, `effectiveUntil`, `lastVerifiedAt`;
- `version` + `status: draft | published | archived`, menggantikan `active` (`isAvailable()` di `programs.js` ikut diganti).

Flow:
1. Create draft.
2. Fill sections progressively.
3. Preview: jalankan `simulateLoan()`/`comparePrimaryPrograms()` (`programs.js`) terhadap input fixture. Rate period divalidasi dengan mengonversinya ke bentuk schedule lalu memanggil `validateRatePeriods()` (`finance.js`); tidak ada validator baru.
4. Publish only when validation complete.
5. Edit produk published membuat baris `draft` dengan `revisionOf`. Publish revisi menaikkan `version` pada id yang sama. Draft user yang memilih versi lama otomatis kena `BANK_PRODUCT_EXPIRED` (410) saat submit, lewat mekanisme `applications.submit` yang sudah ada. Aplikasi yang sudah submit aman karena menyimpan `selection` + `snapshot`.
6. Archive stops future matching but preserves history.

### 4.5 Articles

Shape mengikuti `articles.js`, ditambah field admin:
- `id`, `slug`, `tag`, `icon`, `title`, `summary`, `minutes`, `body: string[]` (paragraf plain text), `status: draft | published | archived`, `updatedAt`;
- `icon` dipilih dari kunci `ARTICLE_ICONS` di `HomePage.jsx` (`percent`, `wallet`, `receipt`, `repeat`, `hand-coins`); ikon baru = tambah ke map itu;
- body dirender sebagai teks per paragraf oleh `EducationPage`, bukan HTML, jadi tidak perlu sanitizer. Tidak ada markdown maupun cover image.

Fitur:
- list/search/filter draft/published/archived;
- preview before publish memakai markup `EducationPage`;
- slug unik dengan format `^[a-z0-9]+(-[a-z0-9]+)*$`; slug artikel yang diarsipkan tetap terpakai, dan slug terkunci setelah terbit karena tautan dan pilihan artikel di Home (`widgetData.js`) mencari lewat slug;
- archive instead of hard delete once published;
- tidak ada lapisan revisi seperti produk: edit artikel terbit langsung tampil, jadi wajib alasan; simpan draft tidak;
- B2C (`explore.get`, `explore.article`) hanya membaca yang `published`.

No generic CMS abstraction.

### 4.6 Reports

Filters: date range, product type, bank, status.

Metrics (sumber data mock dalam kurung):
- registrations (`createdAt` user);
- users with application;
- applications created/submitted/approved/rejected/disbursed (`createdAt`, `submittedAt`, `status`);
- conversion per stage dan average time per stage (`statusHistory`);
- products most selected (`selection.bankProductId`);
- active vs expired products (`status`, `effectiveUntil`).

Tidak ada di MVP:
- eligibility/affordability outcomes: hasil compare/affordability dihitung on-the-fly dan tidak disimpan;
- jumlah pembatalan: cancel = hard delete (doc 04 §9.1), lihat §12 Q4.

Agregat dihitung di `mockApi.js` atas semua akun user di `db.accounts`; frontend tidak menghitung ulang.

Definisi yang dipakai (Phase 7):
- angka periode menghitung kejadian di dalam rentang: pendaftar (`user.createdAt`), pengajuan dibuat (`createdAt`, termasuk draft), diajukan (`submittedAt`), disetujui/ditolak/cair (entri `statusHistory` di rentang);
- tabel tahapan mengikuti kohort yang **diajukan** di rentang, dengan posisi sampai hari ini: jumlah per tahap utama (`submitted → docs_verification → bank_processing → appraisal → approved → akad → disbursed`), konversi dari tahap sebelumnya (bps), dan rata-rata hari di tiap tahap (dari masuk tahap itu sampai masuk tahap berikutnya, termasuk putaran revisi);
- produk paling banyak dipilih dihitung dari `selection` pengajuan yang dibuat di rentang, termasuk draft (hanya agregat);
- filter jenis produk dan bank hanya mempersempit angka pengajuan; jumlah pendaftar tidak terpengaruh;
- default 30 hari terakhir; tanggal dibandingkan per tanggal ISO (UTC di mock, §12 Q5).

Tidak dibuat: filter status (bertabrakan dengan tabel tahapan; daftar Applications sudah punya filter status) dan status katalog aktif/kedaluwarsa (sudah ada di Overview beserta tautannya).

Export CSV is allowed only if backend streams authorized rows and redacts unnecessary sensitive fields. No raw document/identity export. Di mock, operasi API mengembalikan string CSV dan UI mengunduhnya lewat `Blob`.

### 4.7 Configuration

Setiap section memetakan konstanta yang sudah ada. Nilai sekarang menjadi default / versi pertama, jadi perilaku B2C tidak berubah sampai admin mengubahnya.

Sections:
- **Default reminder** — `DEFAULT_REMINDERS` (`seed.js`): payment `[7, 3, 1]`, fixedExpiry `[90, 60, 30, 14, 7]`, channels.
  - Konsumen: `mockApi` (`mortgages.createSetup`, `mortgageFromApplication`) dan `MortgageSetupWizard.jsx`, yang sekarang import langsung dari `@/data/seed` dan harus diganti lewat API.
  - Hanya berlaku untuk setup baru; `mortgage.reminders` user yang sudah tersimpan tidak ditimpa.
  - Set milestone tetap (`FIXED_MILESTONES` di `derive.js` dan `widgetData.js`); admin hanya memilih subset default.
- **Upload** — `MAX_FILE_BYTES` (5MB), `ACCEPTED_TYPES`/`ACCEPTED_EXTENSIONS` (`documentRules.js`).
  - Konsumen: `UploadRow.jsx` (pre-check di client), `mockApi` `applications.uploadDocument` dan `mortgages.markPaid` (bukti bayar).
  - Teks error yang sekarang hardcode ("5MB", "JPG, PNG, atau PDF") diturunkan dari config.
- **Produk** — `CAPACITY_RATIO_BPS` 3500, `STALE_AFTER_DAYS` 30, `OLD_BANK_POLICY` (`catalog.js`).
  - Konsumen: `src/calculations/programs.js` (import langsung). Mock meneruskannya sebagai parameter supaya engine kalkulasi tetap pure.
- **KPR Health formula versions** — lihat di bawah.

"Application operational limits" dihapus karena tidak ada konstanta yang bisa dipetakan. Satu KPR aktif per akun adalah rule produk, bukan config.

Health version = parameter `healthScore()` saat ini. Versi 1 wajib menghasilkan skor yang identik:
- DTI band: ≤30% → 90, ≤35% → 75, ≤40% → 62, ≤50% → 40, selebihnya 20;
- LTV band: ≤50% → 90, ≤70% → 75, ≤80% → 60, ≤100% → 40, selebihnya 20;
- rate risk: floating 50; fixed menurut sisa hari ≤90 → 58, ≤365 → 75, selebihnya 90;
- progress: `min(100, round(50 + 70 × paidRatio))`;
- agregasi: rata-rata komponen yang diketahui, bobot v1 = 1 semua; komponen kosong → `partial`, tanpa nol palsu;
- label: ≥80 Sehat, ≥60 Perlu perhatian, selebihnya Berisiko;
- changelog/reason.

Implementasi:
- `healthScore(input, config = HEALTH_V1)`; `deriveMortgage(m, asOf, healthConfig)` meneruskannya.
- `dashboard.getSnapshot` mengembalikan `healthConfig` aktif (`{version, params}`).
- Pemanggil yang menampilkan skor meneruskan `snap.healthConfig`: `HomePage.jsx` (widget membaca `d.health`), `HealthPage.jsx`, dan `optimize/insights.js`. Pemanggil lain (`MyKprLayout`, `AmortizationPages`, `ApplicationTracker`, `MortgageSetupWizard`, sample widget gallery) tetap memakai default.
- Health page menampilkan versi kalkulasi.

Safety:
- immutable published version;
- draft changes only;
- preview terhadap skenario seed yang sudah ada: `mortgage_active_normal`, `mortgage_active_h90` (warning), `mortgage_active_floating`, `mortgage_partial_property` (nilai properti kosong), ditambah dua input sintetis DTI tinggi dan LTV tinggi;
- before/after skor per fixture; distribusi seluruh user hanya bila backend bisa menghitung;
- publish atomik dan berlaku segera, tanpa penjadwalan;
- rollback publishes previous config as a new version, never mutates history.

Yang dibangun di Phase 8 (detail di §8):
- `HEALTH_V1` di `derive.js` menyimpan ambang di atas dalam bentuk data yang aman untuk JSON: batas DTI/LTV dalam bps, sisa fixed dalam hari, dan band terakhir terbuka (`upTo: null`). `healthScore(input, config = HEALTH_V1)` memberi `tone` per komponen dan `version` pada hasil. Halaman tidak lagi menulis ambang 80/60 sendiri; semuanya membaca `tone`.
- Draft formula hanya ada di editor sampai diterbitkan. Mock tidak menyimpan draft, sehingga tidak perlu CRUD draft dan cek konkurensinya; konkurensi dijaga oleh `expectedVersion` = versi yang sedang berlaku.
- Bagian **Produk** (`CAPACITY_RATIO_BPS`, `STALE_AFTER_DAYS`, `OLD_BANK_POLICY`) **belum** bisa diubah dari admin. Halaman B2C masih menghitung ulang angka-angka ini di browser (`goalConditions`, `dtiTone`, hitung ulang plafon di `ProgramPages`, `PrimaryMilestone`), jadi nilai config hanya akan dipakai sebagian dan hasilnya tidak konsisten. Bagian ini jadi config backend begitu angka-angka tersebut dihitung server.

### 4.8 Audit Log

Fields:
- event ID;
- actor ID/kontak;
- action;
- resource type/ID;
- reason;
- before/after diff (sensitive values masked);
- request ID;

Read-only and append-only from UI. Di mock: `db.auditLog[]`, ditulis oleh setiap operasi `api.admin.*` di `mockApi.js`; "aktivitas admin terbaru" di Overview membaca sumber yang sama.

## 5. Proposed API contract

All under `/api/v1/admin`; Bearer/session auth plus backend role check. Ini kontrak REST untuk backend (snake_case, envelope §6).

## 6. Response envelope and security

Use envelope yang sudah disepakati:

```json
{
  "ok": true,
  "data": {},
  "meta": {
    "request_id": "req_...",
    "api_version": "v1"
  },
  "error": null
}
```

Envelope ini kontrak HTTP. Mock mengembalikan `data` langsung dan melempar `ApiError` (pola `mockApi.js`).

Security requirements:
- role enforcement backend;
- object-level authorization;
- download documents via authorized streaming, never public URL;
- mask NIK/NPWP/account data by default;
- audit every mutation;
- reason required for edits, transitions, publish/archive, and configuration;
- optimistic concurrency (`expected_version`);
- rate limit login/export/download;
- no secrets/tokens in audit before/after;
- CSV protects against formula injection (`=`, `+`, `-`, `@` prefixes);
- session invalidation after role/account state changes;
- catatan internal dan audit disimpan terpisah dari resource aplikasi (`db.adminNotes`, `db.auditLog`), sehingga tidak ikut terkirim lewat `applications.get`/`dashboard.getSnapshot` milik user.

## 11. Risks and mitigations

- **Admin edits financial data:** require reason, version conflict handling, full audit, and recalculation marker.
- **Health config changes all users:** immutable versions, preview fixtures, effective version, rollback-as-new-version.
- **Product revision corrupts old applications:** application stores immutable product/calculation snapshot.
- **Documents contain sensitive data:** authorized streaming, no public path, access audit, no caching of raw files in browser storage.
- **Same frontend leaks admin bundle/UI:** role guard plus backend authorization; optionally lazy-load routes after functionality is stable.
- **Reports expose PII:** aggregate by default; export explicitly whitelists columns.
- **Mock-first diverges from backend:** doc 04 + contract test `mockApi.test.js` + fixtures are completed before UI implementation.
- **Catatan internal bocor ke user:** disimpan di `db.adminNotes`, bukan di objek aplikasi yang dikembalikan endpoint B2C.
- **Mock multi-akun di satu browser berbeda dari backend multi-tenant:** helper menerima `owner`; `httpApi`/backend wajib scope per user id.
- **Config mengubah perilaku B2C diam-diam:** default config = konstanta sekarang; test skor dan batas lama tetap hijau tanpa diubah.
